## What's there

**Modules** (`src/`):
- `money.js` — `parseMoney`, `formatMoney`, `roundCents` (half up, away from zero). Input validation is strict: `1.234`, `abc`, `-5.00`, `12,30` are all rejected; `12.3` and `12.30` both yield 1230 cents.
- `customers.js`, `products.js`, `invoices.js`, `report.js` — the entities and reports from the spec.
- Two helpers not named in the spec: `dates.js` (UTC-based `addDays`/`daysBetween`/`todayISO` so day arithmetic never drifts across DST) and `store.js` (JSON persistence).

**One design decision worth flagging:** since the functions need JSON persistence, every mutating function takes a store handle as its first argument — e.g. `addCustomer(store, { name, email })`, `createInvoice(store, { customerId })`. The payload shape is exactly as specified; the `store` is the `{ path, data }` handle returned by `openStore(path)`. This is documented in the README.

**CLI** (`bin/invoice.js`): all eleven commands. Success prints one JSON value with every money field rendered as a decimal string (`"12.30"`) and exits 0; domain failures print `{"error":"..."}` on stderr and exit 2; unknown commands and missing required options print usage on stderr and exit 1. CSV `export` prints the CSV as a JSON string, quoting fields that contain commas/quotes/newlines.

**Tests** (`test/`): one file per module plus `cli.test.js`, which spawns the real binary and checks exit codes, stdout money formatting, error JSON, and the CSV output.

## Verification

- `npm test` → 36 pass / 0 fail.
- Manual end-to-end run (customer → product → draft → line → issue → partial pay → export → aging → overdue list → revenue) produced correct output: e.g. a $19.99 line, qty 3, 10% discount → net `53.97`, tax `3.78`, total `57.75`; the data file is created under the default `data/invoicing.json` with integer cents, and `exit=1`/`exit=2` were observed for unknown command / not-found / bad amount respectively.

Two of my initial test expectations were wrong (I'd assumed a tax-inclusive total of 3303 instead of 3300, and tried to void an invoice that had a payment); I corrected the tests, not the implementation, since the implementation matched the spec.

One judgment call in `report.js`: `revenue()` groups by issue month for invoices whose status is `issued` or `paid`, so voided invoices are excluded. If you intended voided-but-previously-issued invoices to still count toward revenue, that's a one-line change.
