**What's there**

- `src/store.js` — the shared JSON persistence layer. Default path is `data/library.json` (relative to the working directory, created on first use, including parent dirs). `setDataPath()` lets the CLI point at another file via `--data`. It keeps per-entity id counters (`nextIds`) so ids are assigned in order starting at 1, and it repairs/validates the file on read.
- `src/books.js` — `addBook({ title, author, copies = 1 })`, `listBooks({ available } = {})`. A book is returned as `{ id, title, author, copies, available }`, where `available` is computed from the active loans rather than stored, so it can't drift.
- `src/members.js` — `addMember({ name })` → `{ id, name }`.
- `src/loans.js` — `checkout`, `returnLoan`, `listLoans`, `report`, plus the loan rules.
- `src/dates.js` / `src/validate.js` — small helpers for `YYYY-MM-DD` arithmetic and input validation.
- `bin/library.js` — the CLI with all eight commands.
- `test/` — `books.test.js`, `members.test.js`, `loans.test.js`, `cli.test.js` (module tests use a temp data file; CLI tests spawn the real binary in a temp working directory).
- `README.md` — documents the modules, every command with example output, the storage format and the rules.

**Behavior worth calling out**

Dates are computed in UTC so `YYYY-MM-DD` arithmetic is DST-proof. A book's `available` is `copies` minus its active loans, which is why `list-books --available` and `report.available` agree. Exit codes follow the spec: success prints one JSON value and exits 0; domain/validation failures print `{"error":...}` to stderr and exit 2; unknown commands and missing options exit 1. The CLI also treats a bad integer (`--copies abc`) as a value error (exit 2), since that isn't a *missing* option.

Two judgment calls I made where the spec was silent: `listBooks({ available: true })` keeps books with `available > 0` (parallel to how `--overdue` filters), and `fine` is `0` on an active loan, set only when the loan is returned. `finesOwed` sums only returned loans as specified.
